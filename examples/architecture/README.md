# Sample Control Usage Architecture

This example illustrates how the control requirement generated by the `calm-control-requirement` skill (see [`examples/control-creation`](../control-creation)) is applied within a real CALM architecture, and how to validate that usage with `calm-cli`.

## Contents

```
architecture/
├── sample-control-usage.architecture.json  # Two-node architecture, Sample Control applied to each node
├── url-mapping.json                        # Local resolution for schema URLs not yet published
├── control-requirement-meta.json           # Vendored copy of the CALM control-requirement meta-schema
└── README.md
```

## The Architecture

`sample-control-usage.architecture.json` models a minimal order-processing system:

| Node | Type | Description |
|---|---|---|
| `order-api` | service | Handles order submission and processing requests |
| `order-database` | database | Stores order records and transaction history |

A `connects` relationship (`order-api-to-order-database`, protocol `JDBC`) links the two nodes.

## The Control

Both nodes carry the **Sample Control** (`CTRL-001`) — the requirement generated in [`examples/control-creation/generated-requirements/sample-control-requirement.json`](../control-creation/generated-requirements/sample-control-requirement.json) — each with a different `config` to show the requirement's constraints in action:

| Property | `order-api` config | `order-database` config |
|---|---|---|
| `time-out` | 30 | 60 |
| `latency-range` | 5.0 | 12.5 |
| `protection-level` | high | medium |
| `information-level` | sensitive | very sensitive |
| `control-string` | `order-api-config` | `order-database-config` |
| `control-flag` | true | false |

Each node's `controls.sample-control.requirements[0]` references the requirement schema via `requirement-url` and supplies an inline `config` that must satisfy it.

## Why the URL Mapping Is Needed

The generated requirement's `$id` (`http://calm.finos.org/controls/sample/schema/sample-control.json`) and its `allOf` reference to the CALM control-requirement meta-schema (`http://calm.finos.org/controls/2025-03/meta/control-requirement.json`) are not published, publicly-hosted URLs — they're illustrative placeholders. `url-mapping.json` resolves both to local files so validation can run entirely offline:

```json
{
    "http://calm.finos.org/controls/sample/schema/sample-control.json": "../control-creation/generated-requirements/sample-control-requirement.json",
    "http://calm.finos.org/controls/2025-03/meta/control-requirement.json": "control-requirement-meta.json"
}
```

`control-requirement-meta.json` is a local copy of the official CALM control-requirement meta-schema (bundled with `@finos/calm-cli`), used here so the requirement's `allOf` reference resolves without a network fetch.

## Validating

Run `calm validate` with the URL mapping:

```bash
calm validate -a sample-control-usage.architecture.json -u url-mapping.json -f pretty
```

Expected output:

```
Summary
- Errors: no (0)
- Warnings: no (0)
- Info/Hints: 0

No issues found.
```

This confirms:
- The architecture document itself is structurally valid CALM
- Each node's `sample-control` control block is well-formed
- Each node's `config` satisfies every constraint in the Sample Control requirement schema (numeric ranges, enum values, required properties)

## Trying It Yourself

To see validation catch a violation, try editing a `config` value to break a constraint — for example, set `order-api`'s `protection-level` to `"extreme"` (not in the enum) or `time-out` to `0` (below the `minimum: 1`) — then re-run `calm validate`. The command will report an error pinpointing the invalid property.
