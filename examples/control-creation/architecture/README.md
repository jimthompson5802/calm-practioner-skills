# Sample Control Usage Architecture

This example illustrates how the control requirement generated by the `create-calm-control-req` skill (see [`examples/control-creation`](..)) is applied within a real CALM architecture, and how to validate that usage with `calm-cli`.

## Contents

```
architecture/
├── sample-control-usage.architecture.json  # Two-node architecture, Sample Control applied to each node
├── url-mapping.json                        # Local resolution for schema URLs not yet published
└── README.md
```

## The Architecture

`sample-control-usage.architecture.json` models a minimal order-processing system:

| Node | Type | Description |
|---|---|---|
| `order-api` | service | Handles order submission and processing requests |
| `order-database` | database | Stores order records and transaction history |

A `connects` relationship (`order-api-to-order-database`, protocol `JDBC`) links the two nodes.

## The Control

Both nodes carry the **Sample Control** (`CTRL-001`) — the requirement generated in [`examples/control-creation/generated-requirements/sample-control-requirement.json`](../generated-requirements/sample-control-requirement.json) — each with a different `config` to show the requirement's constraints in action:

| Property | `order-api` config | `order-database` config |
|---|---|---|
| `time-out` | 30 | 60 |
| `latency-range` | 5.0 | 12.5 |
| `protection-level` | high | medium |
| `information-level` | sensitive | very sensitive |
| `control-string` | `order-api-config` | `order-database-config` |
| `control-flag` | true | false |

Each node's `controls.sample-control.requirements[0]` references the requirement schema via `requirement-url` and supplies an inline `config` that must satisfy it.

## Why the URL Mapping Is Needed

The architecture references the generated requirement via `http://example.com/controls/requirements/sample-control-requirement.json`, which is an illustrative placeholder rather than a published URL. `url-mapping.json` resolves that URL to the local generated requirement file so validation can run against the checked-in example:

```json
{
    "http://example.com/controls/requirements/sample-control-requirement.json": "../generated-requirements/sample-control-requirement.json"
}
```

## Validating

Run `calm validate` with the URL mapping:

```bash
calm validate -a sample-control-usage.architecture.json -u url-mapping.json -f pretty
```

Expected output:

```
Summary
- Errors: no (0)
- Warnings: no (0)
- Info/Hints: 0

No issues found.
```

This confirms:
- The architecture document itself is structurally valid CALM
- Each node's `sample-control` control block is well-formed
- Each node's `config` satisfies every constraint in the Sample Control requirement schema (numeric ranges, enum values, required properties)

## Trying It Yourself

To see validation catch a violation, try editing a `config` value to break a constraint — for example, set `order-api`'s `protection-level` to `"extreme"` (not in the enum) or `time-out` to `0` (below the `minimum: 1`) — then re-run `calm validate`. The command will report an error pinpointing the invalid property.
